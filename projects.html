1) Pi-hole Home DNS Deployment (Production Home Network) Raspberry Pi • DNS filtering • Automation

Goal: Reduce ad/tracker traffic and gain DNS-level visibility while maintaining network reliability for all users.

Environment: Raspberry Pi, Pi-hole, home network router (DNS forwarding), multiple client devices

  • What I did:
    • Deployed Pi-hole on a Raspberry Pi to function as the primary DNS resolver for the network.
    • Configured curated blocklists to block tens of thousands of domains associated with advertising, telemetry, and known malicious activity.
    • Validated DNS resolution behavior to ensure normal browsing and streaming services were not disrupted.
    • Developed and used a small maintenance script to automate system updates, Pi-hole gravity updates, cache cleanup, and service restarts.
    • Monitored DNS query logs and rate-limiting behavior to identify noisy or misconfigured clients.
  • Security & operational considerations:
    • Avoided overblocking by gradually tuning blocklists and using targeted whitelisting when required.
    • Ensured DNS availability to prevent single points of failure for the network.
    • Maintained separation between configuration details and public documentation to avoid exposing sensitive information.
  • What I learned:
    • How DNS-based filtering works and where its strengths and limitations exist.
    • How excessive DNS queries can indicate background services, misconfigured devices, or privacy-invasive applications.
    • The importance of automation and routine maintenance for security infrastructure, even in small environments.

2) Incident Response Log Analysis & IOC Extraction SIEM logs • Python parsing • IOC extraction

Goal: Analyze a provided JSON log file containing aggregated SIEM-style data and extract relevant indicators of compromise (IOCs) to support incident response.

Data Source: JSON-based security and system telemetry provided for analysis.

Approach

  • Reviewed JSON log structure to identify relevant fields aligned with incident response requirements.
  • Developed a small Python script to parse and extract relevant indicators of compromise.
  • Focused on producing concise, actionable findings rather than exhaustive raw output.

Indicators of Compromise (Summary)

  • Suspicious IP Addresses:
    • 10.14.22.xx — Internal address observed communicating outside the expected subnet range (10.14.10.0/24).
    • 185.217.1.93 — External IP correlated with suspicious domain activity within the dataset.
  • Suspicious Domains:
    • api-svc-metrics.net — Domain pattern mimicking legitimate telemetry services.
    • update-check.microsoft-service.com — Domain impersonating a trusted vendor naming convention.
  • Suspicious Files / File Paths:
    • C:\Windows\Temp\mcache.dll — DLL located in a temporary directory rather than a standard system path.
  • Suspicious Processes or Commands:
    • Parent: services.exe → Process: powershell.exe — PowerShell launched from a service context.
    • Command: powershell.exe -enc [base64-encoded payload truncated] — Encoded PowerShell command observed (truncated for public reporting).
  • SSL / JA3 Fingerprints:
    • JA3 fingerprint observed on suspicious TLS traffic: 72a589da… (truncated).
  • Accounts Potentially Compromised or Misused:
    • NT AUTHORITY\\SYSTEM — High-privilege execution context associated with PowerShell activity.
    • _svcAdmin — Unsuccessful login attempts correlated with suspicious external activity (name retained as provided in dataset).
  • Suspicious Ports or Protocols:
    • Destination port: 4433 — Observed across multiple connections.

Notes & Next Steps

Observed high-privilege execution context (NT AUTHORITY\\SYSTEM) launching PowerShell with an encoded command, consistent with suspicious automation. A service-style account (_svcAdmin) showed unsuccessful login attempts correlated with suspicious external activity (185.217.1.93). Recommended next steps: isolate affected host(s), review authentication logs for further misuse, collect PowerShell operational logs (if available), and block/monitor the identified external indicators.

3) Multi-Hop SSH Tunneling Across Segmented VMware Networks Kali Linux • Alpine Linux • VMware • SSH Port Forwarding • Hashcat

Goal: Design, build, and document a controlled lab environment demonstrating how SSH local port forwarding can be chained across multiple isolated network segments.

Assignment Scope & Design

The assignment required an SSH port-tunneling environment in which credentials were concealed, discovered, and recovered through password-hash cracking. I designed the implementation by creating the segmented VMware topology, configuring the Linux systems, hosting the credential artifact through a custom web service, and constructing the complete multi-hop tunnel.

Environment & Architecture

  • One Kali Linux system used as the starting point for reconnaissance and tunneling.
  • Six Alpine Linux systems named alpine1 through alpine6.
  • Seven isolated VMware networks spanning VMnet12 through VMnet18.
  • Each Alpine system was dual-homed across two neighboring network segments.
  • SSH was configured on every Alpine system to support controlled remote access.
  • Apache HTTP Server was installed on alpine1 to host the lab’s credential-discovery artifact.

Before tunnel execution, each Alpine system was validated for hostname, network interfaces, SSH service status, and its TCP port 22 listener.

Scenario Implementation

To create the credential-discovery portion of the exercise, I generated NTLM-formatted hashes from intentionally created lab passwords. The hashes were stored in a file named auth_cache.log, placed inside a troubleshooting archive, and hosted through a custom Apache page on alpine1.

These hashes were created specifically for the controlled exercise and were not extracted from Alpine Linux password storage.

Reconnaissance & Credential Recovery

  • Used Netdiscover to identify alpine1 on Kali’s directly connected segment.
  • Used Nmap service detection to identify SSH on TCP port 22 and HTTP on TCP port 80.
  • Accessed the custom troubleshooting portal and downloaded the hosted archive.
  • Extracted the archive and identified the intentionally planted NTLM credential hashes.

Password Auditing

  • Prepared the recovered hashes for processing with Hashcat mode 1000 for NTLM.
  • Used hybrid attack mode -a 6 to test a word followed by a digit-and-symbol mask.
  • Used hybrid attack mode -a 7 to test the same mask before each word.
  • Recovered three passwords with the suffix-based attack and the remaining three with the prefix-based attack.
  • Successfully recovered all six intentionally created lab credentials.

Multi-Hop SSH Tunnel

I created a progressive chain of SSH local port forwards. Each new connection traveled through the forwarding port created by the previous pivot system:

  • 127.0.0.1:1111 reached Box2 through Box1.
  • 127.0.0.1:2222 reached Box3 through Boxes 1 and 2.
  • 127.0.0.1:3333 reached Box4 through Boxes 1–3.
  • 127.0.0.1:4444 reached Box5 through Boxes 1–4.
  • 127.0.0.1:5555 reached Box6 through Boxes 1–5.

Each active SSH session had to remain open because every later forwarding stage depended on the tunnels established before it.

Troubleshooting

  • Resolved SSH daemon restrictions that initially prevented TCP forwarding through intermediate pivot systems.
  • Restarted affected SSH services after correcting forwarding-related configuration.
  • Validated each pivot system’s interfaces and next reachable subnet before extending the tunnel.
  • Separated networking, authentication, service, and forwarding issues during troubleshooting.

Result

Kali successfully authenticated to alpine6 through 127.0.0.1:5555, traversing all five intermediate Alpine systems. The final shell identity, hostname, and network-interface output confirmed that the complete chained tunnel operated successfully.

Security Takeaways

  • Network segmentation reduces direct connectivity but can be bypassed through compromised dual-homed systems.
  • Predictable password structures remain vulnerable to targeted hybrid password attacks.
  • Sensitive internal files should not be exposed through weakly protected web services.
  • SSH TCP forwarding should be restricted when it is not operationally required.
  • Strong authentication, least privilege, and SSH monitoring help reduce lateral-movement risk.
